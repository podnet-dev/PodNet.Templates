# Read-only template drift probe

Run `tools/drift/Detect.ps1` as a **separate process**. It writes one JSON object to stdout. `schemaVersion: 1` includes the SHA-256 of the exact package installed, inferred inputs and their basis, and `{fact, expected, actual}` differences. Exit **0** means clean within the checks below, **1** means drift, **2** means unable to decide. On 2, `reason` explains why; any accumulated deltas are partial, not a completed assessment.

## Running from PodNet.Templates

Requires PowerShell 7.3+, a .NET SDK supporting `-getProperty`/`-getItem` (MSBuild 17.8+), the SDK allowed by the **baseline** global.json, Python 3.8+ and PyYAML. Install the Python requirement in a dedicated virtual environment; pass its interpreter via `-Python` (Windows: `Scripts/python.exe`, Linux: `bin/python`). An isolated Python process does not use user-site packages.

```powershell
python -m pip install -r ./tools/drift/requirements.txt  # in the activated venv
python -B ./tools/drift/test_workflow.py
pwsh -NoProfile -File ./tools/drift/Detect.ps1 -RepoPath ../PodNet.Example -TemplatePackage $package -SdkFeed $feed -Python $python
pwsh -NoProfile -File ./tools/drift/Probe.ps1 -TemplatePackage $package -SdkFeed $feed -Python $python
```

`$package` is a local `.nupkg`, **not** a directory, package ID or glob. Use the modernized template candidate: the older manifest requiring `langVersion`, legacy `.sln`, or reusable publishing workflow is unsupported. `$feed` is an optional local NuGet source for `PodNet.Sdk`; nuget.org remains available for other SDKs. `-SdkVersion` is an optional **caller-chosen baseline input**, not the assessed repository's pin. Omit it for package defaults. `-PrimaryProject` takes a path relative to the assessed repository or an absolute project path inside it.

## Comparison boundary

* `Workspace.ps1` copies inputs excluding `.git`, `.vs`, `node_modules`, `artifacts`, `bin`, `obj`, `TestResults`. Links encountered in the copy are rejected. It installs the local package in a fresh template hive, checks for a unique `pod-nuget-repo` manifest, and rejects post-actions and split manifests. The CLI runs from scratch storage, not the source repository.
* A marker generation discovers the `.csproj` files and how template text wraps description/tags. Primary selection uses a unique `src` project or unique Release-packable `src` candidate. Name comes from evaluated package ID (project name fallback), removing one leading `PodNet.`. Real generation uses `-n`, `-o`, `--targetFramework`, description/tags when nonempty, and optional `--sdkVersion`. No language version is guessed. Input inference uses the outer Release evaluation; configuration-dependent package names/metadata are outside the contract.
* `Detect.ps1` compares generated global.json leaf values **before** applying the generated SDK/test policy to the temporary evaluation copy. Thus a wrong or unavailable actual pin does not prevent comparison or create secondary SDK-default differences. This diagnoses policy differences, not whether the original pin builds. JSON array policies, nested global.json, repo-specific NuGet.Config, and ambiguous solutions are unsupported.
* Seed and omission checks use the template's default framework. For comparison, one baseline is generated per distinct evaluated library framework in Debug and Release; the test may have its own fixed framework. No build, test or restore target runs. SDK resolution itself may download packages.
* Solution membership follows the managed projects, not folder names. If the generated test path is absent, a moved project must be a Debug-runnable, non-integration `.csproj` and uniquely match by filename or evaluated reference to the primary library. Multiple matches or runnable projects with no matching evidence give `unable`; no runnable candidates gives missing-project drift. The selected test's generated library reference is checked per configuration/framework. This identifies roles, not whether CI discovers or executes them.
* Managed build facts are listed in `$managed` in `Detect.ps1`. Output paths are relative to each tree. Package IDs are case insensitive. Referenced requirements compare effective `VersionOverride`, inline `Version`, then active central `PackageVersion`; unreferenced baseline central requirements are also checked. Versions are declaration strings, not resolved versions: `1.0` and `[1.0]` differ. No transitive resolution, full range equivalence, package asset metadata or arbitrary XML comparison. Unknown duplicate item identities fail closed.
* Build comparisons cover evaluated values, including year, package metadata, symbol settings and effective output directories, not the presence of a particular import. An omitted declaration with the same effective default is not drift. Packed file contents, CI-only settings outside the evaluation environment and actual build outputs are not verified.
* `workflow.py` compares the publishing call's owner/ref, baseline permission entries, username source and stage flags. Nugetizer executes a fixed pipeline: token order and repeats do not reorder execution. A valid nonpublishing validation call is ignored even in a conditional or matrix job. Dynamic/invalid stages, multiple publishing calls, publishing conditions/dependencies/matrices, duplicate or merge keys and complex usernames are unsupported.
* The publishing workflow's `on` is compared separately: push tag filters (including `v[0-9]+.[0-9]+.[0-9]+*`), branch filters, release activity types, and bare `workflow_dispatch`/`pull_request` events. Quoting, block/flow style, repeated patterns and reordering literal alternatives do not change the result. Multiple distinct alternatives involving globs, negative patterns, path filters and complex expressions give `unable`; there is no general glob-equivalence solver. Other action inputs, step side effects and effective repository permissions are outside scope.

**Trust boundary:** only run on trusted repositories, template packages, feeds, toolchains, and environments. This is temporary-copy isolation, **not a sandbox**: MSBuild imports/property functions, template generators, and SDK resolvers are executable and may reference locations outside the copy. Use a clean temporary directory outside assessed trees and free of inherited MSBuild/global.json customizations. No promise of offline operation; use a disposable machine for stronger isolation. Handwritten imports relying on excluded outputs or sibling repos are unsupported. The tool does not install missing SDKs or Python packages.

`Probe.ps1` mutates only temporary fixtures. It checks clean generation and harmless edits, relocation and ambiguity, a broadened tag filter, omitted year and changed test output values in Debug and Release, an unavailable actual SDK pin, ambiguous primary selection, and a managed version changed only for Release/net9.0. Consume both the process exit code and JSON; retain the package hash and input paths with the report.
